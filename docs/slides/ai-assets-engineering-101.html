This is the 101 companion, intended for about 15 to 18 minutes including discussion. No knowledge of evaluation tools, coding or HVE-Core is required. AI assets means the reusable guidance around an assistant: instructions, agents and skills. The point is not to memorize those categories. It is to notice that the guidance can affect many pieces of work and therefore deserves its own engineering care. We will use a fictional meeting-summary helper, not real customer data. Every response is authored for teaching; none is captured from a model. The technical evaluation deck is the next lesson, not a prerequisite.
THE CENTRAL IDEA

There are two things to care for

The work produced

Code, plans, summaries and decisions need review.

The guidance reused

The rules shaping that work also need review.

A useful mental model is that we engineer both the work product and the reusable guidance influencing it. The model and runtime are still part of the system; the asset is not a replacement for them. This original conceptual diagram shows influence, not a deterministic guarantee or a deployment. An assistant can misunderstand or ignore a rule. Application code and output review remain necessary. The additional lesson is that a reviewed output does not automatically validate the guidance used to produce it, and well-written guidance does not automatically validate all future outputs.
THREE FAMILIAR RESPONSIBILITIES

An AI asset is reusable guidance

Instruction
A rule: "Do not invent an owner."
Agent
A role: "Act as a careful meeting assistant."
Skill
A repeatable method: "Extract decisions and actions."

The asset guides the model. It is not the model itself.

These are short summaries of responsibilities, not complete artifact schemas. Instructions state rules and context. Custom agents define a focused role and may configure tools. Skills package reusable knowledge and procedures, sometimes with scripts and references. The exact loading mechanism depends on the host. The example sentences are fictional and are not deployed HVE-Core assets. We intentionally focus on instructions, agents and skills rather than surveying every customization type. You do not need to learn file suffixes to understand the engineering obligation.
REUSE INCREASES THE REACH OF A MISTAKE

A small rule can shape many answers

"Turn meeting notes into useful summaries."

Helpful intention

Make each meeting easier to follow.

Unanswered question

What should happen when the notes are incomplete?

Repeated use makes unclear expectations worth fixing.

This is a proposed instruction, not observed production behavior. Ask the audience what useful means: short, complete, accurate, actionable? People can reasonably interpret it differently. A model may also respond differently between runs. The ambiguity is the design problem. Reuse makes it important because a missing rule can recur across tasks. Do not claim that this sentence always causes a particular failure. The next slide gives one fictional example of the risk.
FICTIONAL MEETING / TWO LINES OF NOTES

Looks complete. Is it supported?

Meeting notes

Pilot planned for Friday.
No owner was assigned.

A weak summary

Decision: pilot on Friday.
Owner: Morgan.

Unsupported owner

The answer added a fact the input did not contain.

Pause before naming the issue and ask: where did Morgan come from? Morgan is a fictional name invented in the teaching response. There is no evidence for that owner in the two-line input. We do not need a technical tool to spot this mismatch. The output looks organized and useful, but its completion came at the cost of an unsupported fact. This is the reason to check the input and answer together. This slide makes no claim about actual model performance or pass rates.
HABIT 1 / DEFINE

A contract makes "good" checkable

  1. Summarize decisions from the supplied notes.
  2. Use only owners explicitly named in the notes.
  3. If no owner is named, write "unknown".

Contract = the behavior you expect, including what to do when information is missing.

A written rule guides behavior. It does not guarantee the agent will follow it.

Contract is an engineering term for a shared expectation, not a legal document here. Compare this rule with useful summaries. It names the information source, a factual boundary and the handling of a missing value. A reader can now judge the owner field against the notes. This is still a fictional rule, not a deployed customization. Rules remain advisory prose interpreted by a model; higher-stakes boundaries may also need deterministic permission controls, validation and qualified review.
A MEMORY AID, NOT A NEW TOOL

Define. Try. Check. Improve.

  1. 1. DefineWhat should happen?
  2. 2. TryUse a concrete case.
  3. 3. CheckCompare with the contract.
  4. 4. ImproveRevise and check again.

Keep the case so the same mistake can be caught after the next change.

These four words are an original teaching mnemonic, not the formal HVE Builder phase names or a required universal workflow. They summarize the habits of requirements, trial, evidence review and revision. An improvement is not proven by changing text; it needs another check. Preserve a useful case as a regression test, meaning a check that catches the return of an old problem. We use the phrase first and teach the jargon only when necessary.
PRESENTER-STEPPED / FICTIONAL EXAMPLE

Try the rule on one small case

Use Next step, Back and Reset rather than advancing the whole deck. Step one recalls the contract. Step two puts the exact fictional notes beside a weak response that names Morgan. Pause and invite the audience to spot the mismatch. Step three makes the evidence-based judgment: the owner is unsupported. Step four adds a concrete missing-owner example to the guidance and shows the expected answer for a successful rerun. That answer is a target, not an observed result. No agent, file or customer system is changed. The presenter controls only this authored local sequence. Do not imply the revised wording guarantees a fix; actual testing would still be required.
SAME CONTRACT / DIFFERENT INPUTS

One good example is not enough

Owner supplied
Notes name Morgan.
Expect: owner is Morgan.
Owner missing
No owner is named.
Expect: owner is unknown.
No notes supplied
There is nothing to summarize.
Extend the contract: ask for notes; do not invent a meeting.

Recommended starter cases, not a complete test set or recorded results.

A case is a prepared input with an expected outcome. The first two cases apply the contract already introduced. The third reveals a gap: we also need a rule for absent notes. Explicitly add that requirement rather than claiming the original contract covered it. Start with normal use, a missing value and an absent input. Add cases when experience reveals more important boundaries. Try repeated runs when outputs vary. We do not specify statistical confidence or a required number of trials in this 101 deck; the companion explains those mechanisms.
HABIT 3 / CHECK

Confidence needs something to inspect

A claim

"The summary follows the rules."

Not enough on its own.

Evidence

  • The supplied notes.
  • The resulting summary.
  • The check and why it passed or failed.

A tidy answer and a passing check are different things.

Evidence is the material someone can inspect to assess a claim. For the missing-owner rule, keep the notes, the summary and the check comparing the named owner with the source. A keyword such as owner may establish output shape but not whether the value is supported. This mirrors the HVE-Core coverage distinction between smoke checks and functional evidence. A model saying it complied does not settle the question. File effects and tool actions require appropriate observations when those are part of the contract. We are not teaching trajectory schemas or graders yet.
HABIT 4 / IMPROVE

A guidance change is an engineering change

Explain it
Which behavior should change, and why?
Review it
Who owns the rule and can check the boundary?
Recheck it
Keep a version and rerun the relevant cases.

"We changed the words" is not the same as "we verified the behavior".

Version means an identifiable revision of the asset, so a result can be associated with the text that produced it. Ownership means someone can explain the intent and approve the change according to the team's process. These are recommended engineering habits rather than a claim that every organization uses one process. In HVE-Core, the authoring workflow owns review and validation and CI links changed assets to cases. Rerun important cases after a change, and check whether previously correct behavior was lost. For a hard boundary, add appropriate controls instead of relying solely on instruction wording.
A BRIDGE TO THE REAL REPOSITORY

HVE-Core makes these habits concrete

Author and review
HVE Builder helps develop reusable AI assets.
Link a change to cases
Evaluation specs identify the assets they test.
Run and inspect
Vally runs configured cases and returns grading evidence.

The evaluation companion explains how the cases, checks and results are wired together.

HVE-Core is the reusable AI-asset repository supporting Hyper Velocity Engineering. HVE Builder has an authoring, review and validation contract. Changed AI assets must have evaluation backlinks in the repository's CI process. Vally is the framework used for model-backed case execution and grading, while some checks are static and need no model. These are implemented surfaces read at the pinned checkout, not results of a new run. The meeting-summary helper is not a deployed HVE-Core asset and the synthetic cases have not been added to evals. This slide maps the habits to actual capabilities without requiring tool syntax.
PAUSE / DISCUSS / RECALL

Would you accept this answer?

"The format looks right, so the asset is ready."

What evidence is still missing?

Reveal the answer

Check the facts against the input, try missing-input cases and identify the asset version tested. Correct formatting alone does not establish correct behavior.

Give the audience time to answer before opening the local disclosure. This is a recall opportunity, not a live exam or evidence of comprehension. A good response names the input, actual output and expected behavior; stronger responses also ask about a missing owner and whether the tested revision is the one being shared. The disclosure is a native browser control, works with keyboard input and does not call any model. Reinforce that a rule can be clear yet still need evidence of observed behavior.
A PRACTICAL START

Choose one recurring task

  1. Write what good behavior means.
  2. Save a normal case and a missing-input case.
  3. Review the actual answers with an owner.
  4. Change one thing, then check again.

Start small enough that another person can inspect the whole example.

Do not create a customization merely because a tool supports one. Start with an observed recurring problem. If the existing behavior already meets the need, a new asset may be unnecessary. Use permitted synthetic or privacy-reviewed examples rather than casually putting customer data into tests. The four actions are a recommended low-complexity starting point, not a substitute for governance or domain-specific review. For actions that could cause harm or change shared systems, stronger controls and approval may be required.
