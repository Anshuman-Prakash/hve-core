HVE-Core is the reusable asset repository for Hyper Velocity Engineering. HVE-Core contains reusable instructions, agents and skills that guide AI-assisted work. A small wording change can alter routing, decisions or produced files. The repository therefore treats these assets as versioned engineering inputs, with tests beside their contracts. This is a roughly 25-minute introduction. We will explain the architecture first, introduce the vocabulary, then examine actual evaluation specifications. We did not execute model-backed evaluation suites to make this presentation, and this talk makes no current pass-rate claim.
THE BIG PICTURE

HVE-Core defines the behavior.
Vally measures a run.

Separate the product we test from the framework that tests it. HVE-Core assets tell the assistant what to do. HVE-Core evaluation specs describe situations and the evidence that should count. Vally executes those specs, using the Copilot software development kit, or SDK, as an agent runtime. The runtime connects the model to tools and a workspace. CI means automated checks associated with a code change. HVE-Core's CI wrappers connect changed assets to relevant cases and validate the returned evidence. This is an original conceptual diagram, not a deployment diagram or a claim that every check invokes a model.
DEFINE THE THING WE TEST

Markdown can carry executable intent

Instruction
A rule for a working context: how to write a documentation page.
Agent
A role and workflow: plan, review, coach or coordinate.
Skill
Task knowledge, references and sometimes scripts: a reusable capability.

A behavior contract says what should happen, when it applies and where the assistant must stop.

An AI asset is not the underlying model. This talk covers three customization categories: instructions, agents and skills. A contract can require an output format, a decision gate, a particular artifact, or a refusal to cross a write boundary. The asset is stored in source control and reviewed like code because its text affects behavior. Not every agent test literally invokes a native agent. We will return to that distinction when we examine coverage. These definitions are beginner-oriented summaries, not an exhaustive client-specific schema. The word prompt elsewhere means an evaluation input or Vally grader type, not a separate asset category.

FIVE TERMS, ONE PIPELINE

From test input to explainable result

  1. 1 / INPUT

    Stimulus

    A prompt or conversation plus checks.

  2. 2 / RUN

    Executor

    Sets up and runs the agent.

  3. 3 / RECORD

    Trajectory

    Events, metrics and final output.

  4. 4 / CHECK

    Graders

    Assertions or judgments with evidence.

  5. 5 / RESULT

    Score

    Aggregate result under a scoring rule.

A trial is one execution of one stimulus. A suite selects a related collection of test cases.

A stimulus is a test case, not merely an isolated question. It may also specify files, skills, resource limits and graders. An executor manages the run. The Copilot SDK executor is the maintained behavior-testing path in HVE-Core. A trajectory records the response and tool activity rather than only the last sentence. Each grader looks for a particular property and supplies evidence. Vally aggregates grader scores and determines a verdict according to the spec. Repeating a stimulus produces multiple trials. Static lint checks can inspect assets directly, without this agent-execution path.

BEHAVIOR LEAVES A TRACE

Inspect the journey, not only the answer

Two agents can give the same answer while taking different actions.

  • Did a tool fail?
  • Was a skill activated?
  • Did it write a file?
  • How long did the trial take?

A trajectory is diagnostic evidence. HVE-Core public CI artifacts publish safe summaries, not raw transcripts.

Trajectory events include messages, tool calls and results, skill activations, token usage, errors and turn boundaries. Metrics aggregate those observations. Token usage describes model input and output volume, not correctness. The displayed field map is illustrative and deliberately excludes fabricated timings or token counts. A trajectory can include sensitive output and tool arguments. HVE-Core's public CI policy withholds raw trajectories and judge console logs while publishing bounded summaries. Do not confuse observability with proof: a tool call can establish that an action was attempted, while a result or file assertion is needed to establish its effect.

Taxonomy describes determinism, cost, reference needs, scope and scoring method. The spec still chooses its graders explicitly.

A grader is an assertion or evaluator. A rubric is a written definition of the desired behavior used by a model judge. Prefer a deterministic check when it can credibly decide the requirement, such as a named file with a required field. Use a semantic judge when the requirement is about meaning, but calibrate it and inspect disagreements. A deterministic grader will repeat the same verdict for the same input; this does not guarantee that its assertion is adequate. Taxonomy helps choose checks for the local loop, CI or a more expensive scheduled run. HVE-Core primarily extends coverage through specifications, fixtures and orchestration; this deck does not claim a shipped custom-grader plugin.
RESULT SCHEMA

Keep passed and score distinct

namekindpassed: booleanscore: 0..1evidence

No threshold

Every grader must pass.

1, 1, 0 → score 0.667
Trial FAIL

Threshold = 0.6

The aggregate score decides.

1, 1, 0 → score 0.667
Trial PASS / one failed check

Illustrative equal-weight scores. Type weights average graders of the same type first; an eval-level mean can also carry a weak stimulus.

The grader result contract includes a name, kind, binary passed flag, numeric score and evidence. Some results include nested details. A score and a binary result need not agree. With no scoring threshold, Vally requires every grader to pass. With a threshold, the trial score determines the verdict, so a failed check can be carried by others. Explicit weights operate by grader type, not by each grader name. Execution errors still fail the eval; a permissive threshold does not turn an unexecuted case into success. The numeric example assumes each check gives one for pass and zero for fail. HVE-Core diagnostics preserve thresholdPassed and allGradersPassed separately to make this distinction visible.
AI OUTPUT VARIES

One good answer is a weak reliability claim

Trial 1
PASSTrial 2
PASSTrial 3
FAIL
pass@k
Chance of at least one success among k trials.
pass^k
Chance that all k trials succeed.
Flakiness
A stimulus has both passing and failing trials.

HVE-Core defaults vary: skill quality 3 trials; agent behavior 5; planner conformance 1. These are configured budgets, not statistical certification.

The three boxes are fictional trials, not HVE-Core results. Repeated runs help reveal variation caused by the agent or judge. pass@k rewards getting at least one success; pass^k asks about consistent success. Vally's pass@k estimate uses a combinatorial estimator, while pass^k derives from the observed success probability raised to k. Neither metric repairs a weak grader or an unrepresentative test set. HVE-Core's YAML declares different run budgets, and individual stimuli may override defaults. Although the general contribution guide recommends multiple model-backed trials, the current planner-conformance specs default to one. Report the actual configuration instead of implying every suite repeats all cases.

Two turns establish the planner context

Turn 0: launch the staged RAI Planner.

Turn 1: present an unreviewed loan-decision scenario.

What the rubric asks

Recognize consequential risk to people rather than treating it as routine automation.

The prompt judge grades turn 1. Its weight is 0.7; the threshold is 0.7. Budget checks alone cannot carry the case.

RAI means Responsible AI. The RAI Planner spec stages its agent and dependencies, then sends a launch directive followed by the case. The judge evaluates the second turn against the rubric, rather than merely looking for a keyword. A wall-time check limits the completion budget. The declared type weights are prompt 0.7, wall-time 0.15 and output-contains 0.15, with threshold 0.7. This particular stimulus has a prompt and wall-time grader, and Vally renormalizes weights over types that actually ran. Therefore do not describe it as an unconditional binary judge veto: its score and present check types still matter. These planner suites run through the scheduled agent-conformance workflow, not the PR changed-artifact lane. Their current default is one trial.
A / B REGRESSION QUESTION

Does the customization change ordinary answers?

Current subject: RPI Agent. Three trials are a provisional budget. Comparison evidence is report-only under the current calibrated-policy boundary.

A/B testing changes one factor while keeping the question and execution model consistent. HVE-Core's baseline-equivalence suite compares the base environment with a materialized RPI Agent. RPI stands for Research, Plan and Implement; the agent also coordinates review. The comparison contract tells the judge to call a tie when both answers satisfy the behavioral requirement. Otherwise a preference judge may reward wording rather than actual sameness. The present corpus and scope guards are specific to RPI Agent; materializing another agent does not make the corpus valid for that subject. The devloop tier is advisory; calibration and ci tiers keep comparison reporting distinct from authoritative structural and deterministic evidence. Do not claim statistical certification from the provisional three-trial budget.
REPOSITORY-SPECIFIC ORCHESTRATION

Connect each change to its evidence

  1. 1. DiscoverChanged AI assets and changed stimuli.
  2. 2. ResolveBacklinks select cases; shared run keys are deduplicated.
  3. 3. ExecuteA bounded plan assigns trials to shards.
  4. 4. ReconcileFan-in validates every expected producer.
Asset slug: docusaurus-edits↔tags.instruction: docusaurus-edits

Coverage presence is required for changed AI assets. A changed test can run even when its referenced asset did not change.

A backlink connects a stimulus to the asset kind and slug. The slug comes from the file or skill name. The presence check fails when a changed asset has no matching test. Changed stimuli are also discovered, so an assertion change cannot escape execution merely because the asset is unchanged. Shared specs use tag-scoped selection to avoid grading unrelated cases as an asset's own coverage. HVE-Core deduplicates run keys and keeps connected artifacts cohesive when planning shards. A shard is a bounded portion of the workload; a producer is the job returning its evidence. Fan-in means bringing those outputs together and checking completeness. These wrappers, safety rules and evidence contracts are HVE-Core extensions around Vally, not a separate executor or a claimed custom grader implementation.
A GREEN SUMMARY NEEDS A COMPLETE RECORD

Missing evidence must not look like success

Behavioral outcome

  • Scores and threshold verdicts.
  • Every grader's pass / fail.
  • Advisory versus blocking policy.

Evidence integrity

  • Expected cases, trials and graders.
  • Execution and grading status.
  • Matching input and plan digests.

An integrity failure blocks a producer even when its behavioral cases are advisory.

Public summaries omit raw responses and tool arguments. Fork PRs run unprivileged presence/lint checks; credentialed execution is skipped.

HVE-Core's ordinary producer diagnostics expose declared models, input identity, expected cases, attempts, trial results and grader identities. thresholdPassed describes the score policy; allGradersPassed records a different property. The attempt selection chooses the run with the fewest ungraded trials and keeps the first on ties, while preserving the other attempts. Missing, duplicated, malformed or unusable selected evidence can cause integrity-failure independently of advisory behavior. Global fan-in validates planned producers, ownership and arithmetic. The report job presents the authoritative summary rather than deciding completeness itself. The credential boundary skips model-backed runs for fork PRs and merge groups; a skip is not a pass. Public artifacts contain safe aggregate and bounded debugging projections rather than transcripts. This is the implemented contract, not evidence of a current run.
FROM CONTRACT TO REGRESSION TEST

Make the intended behavior reviewable

  1. State the contractExpected result, applicable context and stop boundary.
  2. Build representative casesNormal use, missing inputs, resume state and out-of-scope use.
  3. Stage and assertDeclare dependencies; choose output, file, tool or semantic checks.
  4. Link, validate and calibrateAdd the kind/slug backlink; inspect failures before promoting a gate.

Behavior-conformance graduation: ≥30 advisory CI runs, ≤5% rolling 7-day false positives, CODEOWNERS approval, then a rollback window.

A useful case starts with a specific requirement rather than a generic prompt asking whether an agent is good. Synthetic fixtures let you test state recovery and missing inputs without exposing real customer material. Bleed-detection tests check that a skill does not apply outside its intended scope. Backlinks are what make the CI selection connect a change to its own cases. For generated agent behavior, edit the per-agent partial and regenerate the combined spec. The current advisory graduation policy requires at least 30 CI observations, no more than 5% human-confirmed false positives over seven days, and CODEOWNERS approval. The policy also requires rollback if the first 14 days exceed the limit. Those values are policy requirements, not claims that every current stimulus has achieved calibration. Model-backed lanes need separate prerequisites and authorization.
CALIBRATED CONFIDENCE

Extensive testing is a discipline, not a guarantee

What you can inspect

  • Versioned behavior contracts and cases.
  • Repeatable checks and explicit rubrics.
  • Contained artifacts and complete run evidence.

What a pass cannot promise

  • Correctness outside the tested scenarios.
  • Semantic truth from keyword matches.
  • All-agent equivalence or zero model variation.

Ask: which asset was loaded, which requirement was checked, and what evidence would reject the claim?

This is the central engineering habit: be precise about what evidence can decide. More cases increase breadth but do not fix a weak assertion. Repeated trials expose variation but cannot establish representativeness. A semantic judge evaluates meaning but remains a fallible model. File-effect tests demonstrate contained effects, not a live production outcome. An advisory finding is still useful even though it is not a blocker. A blocking integrity rule makes evidence trustworthy without establishing that every behavioral requirement is correct. The source-backed inventory in this deck must not be presented as a live pass rate, certification or full coverage guarantee.
