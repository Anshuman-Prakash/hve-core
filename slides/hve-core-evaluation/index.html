HVE-Core is the reusable asset repository for Hyper Velocity Engineering. HVE-Core contains reusable instructions, agents and skills that guide AI-assisted work. A small wording change can alter routing, decisions or produced files. The repository therefore treats these assets as versioned engineering inputs, with tests beside their contracts. This is a roughly 25-minute introduction for a general audience; no knowledge of Copilot, YAML or evaluation tools is assumed. We will explain the architecture first, introduce the vocabulary, then examine actual evaluation specifications. Sources were checked on October 11, 2026 against main commit 49dfb7386. We did not execute model-backed evaluation suites to make this presentation, and this talk makes no current pass-rate claim.
THE BIG PICTURE

HVE-Core defines the behavior.
Vally measures a run.

Separate the product we test from the framework that tests it. HVE-Core assets tell the assistant what to do. HVE-Core evaluation specs describe situations and the evidence that should count. Vally executes those specs, using the Copilot software development kit, or SDK, as an agent runtime. The runtime connects the model to tools and a workspace. The lower lane explains HVE-Core continuous integration (CI): automated checks associated with a code change. First, its wrappers select cases linked to changed assets. Then Vally runs those selected cases and captures trial evidence. HVE-Core verifies that the expected results are complete before reporting findings and applying advisory or blocking policy. Selection happens before execution; evidence validation and reporting happen afterward. Findings inform the next asset revision rather than automatically rewriting it. This is an original conceptual diagram, not a deployment diagram or a claim that every check invokes a model.
DEFINE THE THING WE TEST

Markdown can carry executable intent

Instruction
A rule for a working context: how to write a documentation page.
Agent
A role and workflow: plan, review, coach or coordinate.
Skill
Task knowledge, references and sometimes scripts: a reusable capability.

A behavior contract says what should happen, when it applies and where the assistant must stop.

An AI asset is not the underlying model. This talk covers three customization categories: instructions, agents and skills. A contract can require an output format, a decision gate, a particular artifact, or a refusal to cross a write boundary. The asset is stored in source control and reviewed like code because its text affects behavior. Not every agent test literally invokes a native agent. We will return to that distinction when we examine coverage. These definitions are beginner-oriented summaries, not an exhaustive client-specific schema. The word prompt elsewhere means an evaluation input or Vally grader type, not a separate asset category.

VALLY ARCHITECTURE / THE FULL PICTURE

How Vally runs and grades a test

This original diagram summarizes Vally's official The Full Picture architecture rather than copying its ASCII illustration or example result numbers. Read top to bottom: eval.yaml defines a stimulus, the selected graders and shared execution defaults. A stimulus is a prompt or conversation plus test configuration, and may also declare files, skills and resource limits. The executor prepares the workspace and runs the agent through the Copilot SDK in HVE-Core's maintained behavioral-evaluation path. It captures a trajectory containing typed events, computed metrics and the final output. That recorded run feeds the configured graders, illustrated here by text checks, file checks and a model judge. These are possible grader families, not three checks that every case must run. Workspace graders can also inspect produced files in the disposable trial workspace; the trajectory connects them to that workspace. Each grader returns passed, a numeric score and evidence. Vally aggregates those results under the spec's scoring rule to produce a score and verdict. The branch lines show that multiple checks inspect one run; they do not promise concurrent execution. The score is not automatically the same as every grader passing. No fabricated score, timing, token count or live outcome appears. One executor run is one trial; repeating a stimulus produces multiple trials. A suite selects a related collection of test cases. Static lint graders inspect assets directly without this agent-execution path.
BEFORE THE RUN / DEFINE THE TEST

A test defines the task and the checks

Real example: the functional code-review test

Task
Review a code change for logic, errors and severity.
Checks
Look for findings; reject claims that source files were edited.
Run budget
Five trials, up to five minutes each.

Define what counts as success before asking the agent to act.

Vally terms: task = stimulus; checks = graders; run budget = defaults.

A test specification is a reviewable engineering asset: it defines what to ask, what evidence to check and how to bound the run. The visible example summarizes code-review-functional-lens from the agent-behavior suite. Its prompt asks for review of logic, edge cases and error handling with severity; its two output-matches graders check finding vocabulary and negate affirmative source-edit claims. These checks are limited: vocabulary does not prove correctness and an edit claim is not a filesystem observation. The case inherits defaults.runs: 5, defaults.timeout: 300s and executor: copilot-sdk, so the displayed budget is five trials of up to five minutes, not measured execution. YAML is human-readable structured configuration. In eval.yaml, name identifies the eval and type distinguishes capability assessment from regression intent. stimuli contains named cases with prompt or turns and graders. defaults supplies shared executor, run count and timeout unless a case overrides them. tags selects cases and links them to assets; the generator adds agent: code-review-functional to this case. scoring configures optional type weights and a threshold; agent-behavior uses threshold 0.7. This case carries advisory: true, an HVE-Core wrapper policy, not a universal Vally grader rule. The later walkthrough shows the exact authored prompt and grader patterns. The test environment controls which assets the agent can use. A fixture is a prepared test input, such as a synthetic state file or sample document; it is not customer data. The RAI Planner conformance spec stages its agent, shared instructions and delegated skills. Its source list includes rai-planner and rai-standards skills plus the agent and shared instruction files. src resolves relative to the eval-spec directory; dest names the path inside the temporary trial workspace. Current Vally calls this agent_environment; environment is a deprecated alias still found in some HVE-Core specs. grading_environment can stage grader-only files after the agent finishes, keeping hidden checks out of the agent's workspace during execution. Do not infer that every spec uses hidden grading files. Merely copying an .agent.md file to its normal path does not establish that it entered model context; a present file also does not prove it was read. Trajectory = the recorded behavior of one trial.

HVE-Core publishes bounded summaries, not raw transcripts.

A trajectory records the agent's behavior during one trial rather than only its final answer. The left-hand response is an authored illustration grounded in the division-function test; it is not a live model response. The right-hand categories describe record fields, not a claim that particular tools or skills ran. Vally trajectory events include user_message, assistant_message, tool_call, tool_result, skill_activation, token_usage, error and turn_start/turn_end. Computed metrics include tokenUsage, toolCallCount, skillActivationCount, turnCount, wallTimeMs and errorCount; finalOutput is the final agent response. Token counts describe usage, not correctness. We show no fabricated timing or token measurements. Two identical final answers can have different action histories, failures and resource usage. A tool call establishes an attempted action; inspect its result or use a workspace assertion to establish its effect. Sensitive output and tool arguments may appear in trajectories. HVE-Core public CI withholds raw trajectories and judge console logs, publishing bounded diagnostic summaries instead. Observability is evidence, not proof of every behavioral claim.

Taxonomy describes determinism, cost, reference needs, scope and scoring method. The spec still chooses its graders explicitly.

A grader is an assertion or evaluator. A rubric is a written definition of the desired behavior used by a model judge. Prefer a deterministic check when it can credibly decide the requirement, such as a named file with a required field. Use a semantic judge when the requirement is about meaning, but calibrate it and inspect disagreements. A deterministic grader will repeat the same verdict for the same input; this does not guarantee that its assertion is adequate. Taxonomy helps choose checks for the local loop, CI or a more expensive scheduled run. HVE-Core primarily extends coverage through specifications, fixtures and orchestration; this deck does not claim a shipped custom-grader plugin.

Illustrative results, not HVE-Core measurements. A passing score or repeated successes cannot repair a weak grader.

Start with the left panel: a verdict for one trial. The grader result contract includes a name, kind, binary passed flag, numeric score from 0 to 1 and evidence; some results include nested details. A score and a binary result need not agree. With no scoring threshold, Vally requires every grader to pass. With a threshold, the trial score determines the verdict, so a failed check can be carried by others. The displayed equal-weight scores give one for pass and zero for fail: (1 + 1 + 0) / 3 is approximately 0.667. This fails without a threshold, but passes at 0.6 despite one failed check. Explicit weights operate by grader type, averaging graders of the same type first, not by each grader name. An eval-level mean can also carry a weak stimulus. Execution errors still fail the eval; a permissive threshold does not turn an unexecuted case into success. HVE-Core diagnostics preserve thresholdPassed and allGradersPassed separately. Then move to the right panel: repeated executions of the same stimulus. The three boxes are fictional trials, not HVE-Core results. Repeated runs help reveal variation caused by the agent or judge. pass@k estimates the chance of at least one success among k trials using a combinatorial estimator. pass^k estimates the chance that all k trials succeed from the observed success probability raised to k. Flakiness means a stimulus has both passing and failing trials. Neither metric repairs a weak grader or an unrepresentative test set. HVE-Core defaults vary: skill quality uses 3 trials, agent behavior 5, and planner conformance 1, with per-stimulus overrides possible. These are configured budgets, not statistical certification. Although general contribution guidance recommends multiple model-backed trials, the current planner-conformance specs default to one. Report the actual configuration rather than implying every suite repeats all cases.

REPOSITORY-SPECIFIC ORCHESTRATION

Connect each change to its evidence

  1. 1. DiscoverChanged AI assets and changed stimuli.
  2. 2. ResolveBacklinks select cases; shared run keys are deduplicated.
  3. 3. ExecuteA bounded plan assigns trials to shards.
  4. 4. ReconcileFan-in validates every expected producer.
Asset slug: docusaurus-edits↔tags.instruction: docusaurus-edits

Coverage presence is required for changed AI assets. A changed test can run even when its referenced asset did not change.

A backlink connects a stimulus to the asset kind and slug. The slug comes from the file or skill name. The presence check fails when a changed asset has no matching test. Changed stimuli are also discovered, so an assertion change cannot escape execution merely because the asset is unchanged. Shared specs use tag-scoped selection to avoid grading unrelated cases as an asset's own coverage. HVE-Core deduplicates run keys and keeps connected artifacts cohesive when planning shards. A shard is a bounded portion of the workload; a producer is the job returning its evidence. Fan-in means bringing those outputs together and checking completeness. These wrappers, safety rules and evidence contracts are HVE-Core extensions around Vally, not a separate executor or a claimed custom grader implementation.
A GREEN SUMMARY NEEDS A COMPLETE RECORD

Missing evidence must not look like success

Behavioral outcome

  • Scores and threshold verdicts.
  • Every grader's pass / fail.
  • Advisory versus blocking policy.

Evidence integrity

  • Expected cases, trials and graders.
  • Execution and grading status.
  • Matching input and plan digests.

An integrity failure blocks a producer even when its behavioral cases are advisory.

Public summaries omit raw responses and tool arguments. Fork PRs run unprivileged presence/lint checks; credentialed execution is skipped.

HVE-Core's ordinary producer diagnostics expose declared models, input identity, expected cases, attempts, trial results and grader identities. thresholdPassed describes the score policy; allGradersPassed records a different property. The attempt selection chooses the run with the fewest ungraded trials and keeps the first on ties, while preserving the other attempts. Missing, duplicated, malformed or unusable selected evidence can cause integrity-failure independently of advisory behavior. Global fan-in validates planned producers, ownership and arithmetic. The report job presents the authoritative summary rather than deciding completeness itself. The credential boundary skips model-backed runs for fork PRs and merge groups; a skip is not a pass. Public artifacts contain safe aggregate and bounded debugging projections rather than transcripts. This is the implemented contract, not evidence of a current run.
FROM CONTRACT TO REGRESSION TEST

Make the intended behavior reviewable

  1. State the contractExpected result, applicable context and stop boundary.
  2. Build representative casesNormal use, missing inputs, resume state and out-of-scope use.
  3. Stage and assertDeclare dependencies; choose output, file, tool or semantic checks.
  4. Link, validate and calibrateAdd the kind/slug backlink; inspect failures before promoting a gate.

Behavior-conformance graduation: ≥30 advisory CI runs, ≤5% rolling 7-day false positives, CODEOWNERS approval, then a rollback window.

A useful case starts with a specific requirement rather than a generic prompt asking whether an agent is good. Synthetic fixtures let you test state recovery and missing inputs without exposing real customer material. Bleed-detection tests check that a skill does not apply outside its intended scope. Backlinks are what make the CI selection connect a change to its own cases. For generated agent behavior, edit the per-agent partial and regenerate the combined spec. The current advisory graduation policy requires at least 30 CI observations, no more than 5% human-confirmed false positives over seven days, and CODEOWNERS approval. The policy also requires rollback if the first 14 days exceed the limit. Those values are policy requirements, not claims that every current stimulus has achieved calibration. Model-backed lanes need separate prerequisites and authorization.
CALIBRATED CONFIDENCE

Extensive testing is a discipline, not a guarantee

What you can inspect

  • Versioned behavior contracts and cases.
  • Repeatable checks and explicit rubrics.
  • Contained artifacts and complete run evidence.

What a pass cannot promise

  • Correctness outside the tested scenarios.
  • Semantic truth from keyword matches.
  • All-agent equivalence or zero model variation.

Ask: which asset was loaded, which requirement was checked, and what evidence would reject the claim?

This is the central engineering habit: be precise about what evidence can decide. More cases increase breadth but do not fix a weak assertion. Repeated trials expose variation but cannot establish representativeness. A semantic judge evaluates meaning but remains a fallible model. File-effect tests demonstrate contained effects, not a live production outcome. An advisory finding is still useful even though it is not a blocker. A blocking integrity rule makes evidence trustworthy without establishing that every behavioral requirement is correct. The source-backed inventory in this deck must not be presented as a live pass rate, certification or full coverage guarantee.
